| --- | --- |

| Fuga attraverso l'orchestratore: un brief scritto dal modello locale dopo aver letto L2 | Taint e clearance (D-015): contesto per task, conversazioni di lavoro a L1, declassamento solo con approvazione del testo esatto |
| Esecutore cloud che legge file fuori dal compito | Confinamento (D-014): allowlist, cartella del progetto come unica cartella leggibile (D-056) o copia per run, scansione preventiva, sandbox, canarino |
| Esecutore cloud che eredita connettori e impostazioni del profilo utente | Solo i server MCP di Arianna, nessuna impostazione utente caricata; verificato dal test di contratto |
| Strumento MCP che restituisce L2 a una sessione cloud | Il server degli strumenti conosce la clearance della sessione e nega sopra L1 |
| Contenuti L2 su Telegram o al telefono | Canali esterni dietro gateway (D-016): al massimo L1, L2 come riferimento |
| Prompt injection da contenuti non fidati | Lethal trifecta rimosso per scheda; Dual LLM; nessun invio esterno senza approvazione |
| Agente che esegue comandi dannosi | Permessi minimi (`--allowedTools`), sandbox, worktree; approvazione per le azioni irreversibili |
| Furto o abuso delle credenziali | `sops` + `age` (`@arianna/vault`, D-042): chiave age fuori da `ARIANNA_HOME`, `sops` lanciato con un ambiente ridotto, valore solo con `reveal()`; il gateway blocca ogni uscita che contiene un valore rivelato; nessun token OAuth estratto; L3 solo come riferimenti; ambiente pulito per i processi figli |
| Catena di fornitura (pacchetto, server MCP o skill ostile) | Versioni esatte e lockfile con hash in git; nessuna release più giovane di un giorno (`minimumReleaseAge`); script di installazione dei pacchetti non eseguiti; ogni dipendenza ha una voce in `DECISIONS.md`; server MCP in container senza accesso ai dati privati |
| Costi o cicli fuori controllo | Tetti di passi, tempo, costo/quota per task; scheduler deterministico |
| Manomissione del registro | Eventi append-only con catena di hash, verificata da `arianna doctor` |
| Accesso remoto al server | VPN (WireGuard o Tailscale), nessuna porta esposta, autenticazione sull'HUD |
| Pagina web ostile che usa il browser dell'utente contro l'API locale (DNS rebinding, CSRF, WebSocket da un altro sito) | API solo su loopback; `Host` ammesso solo se è l'indirizzo del core; `Origin` dello stesso host per scritture e WebSocket; scritture solo in JSON; nessun header CORS; CSP stretta (D-039). Fino all'autenticazione (1.13) ogni processo locale può usare l'API: gli esecutori cloud ne sono esclusi dalla sandbox (1.6) |
| Chiamate telefoniche | Audio nel cloud: nessuna lettura di L2 (regola 10; D-110), i dettagli solo nella chiamata via internet o VPN; numeri ammessi in lista |
| Cambio regole degli abbonamenti | Adattatori sostituibili, test di contratto, controllo periodico delle pagine ufficiali |
| Perdita di dati | Backup cifrati di archivio, KB e database; ripristino provato in Fase 2 |

## Regole di sviluppo

- Dati finti ovunque in sviluppo; i dati veri entrano solo dopo il criterio di uscita della Fase 1A.
- Ogni azione esterna o irreversibile è registrata e, salvo autonomia esplicita, approvata.
- I permessi in `.claude/settings.json` negano file di segreti, `curl`, `wget` e `git push`; non si usano divieti larghi come `Read(~/**)`, perché il repository stesso sta nella home e resterebbe illeggibile.
- Il blocco fuori dal repository è affidato all'hook `.claude/hooks/block-outside-repo.js`:
  - per `Read`, `Edit`, `Write`, `Grep`, `Glob` e `NotebookEdit` il controllo è stretto: ogni percorso fuori dal repository è negato, symlink compresi;
  - per `Bash` è un'euristica: nega i comandi che nominano percorsi nella home, in `/Users`, `/Volumes` e simili fuori dal repository. Si aggira con variabili o sottocomandi, quindi è una rete di sicurezza contro gli errori, non una sandbox;
  - se l'input non è leggibile, l'hook nega (fail-closed); se invece lo script va in errore prima di partire, Claude Code prosegue senza blocco, quindi i suoi test girano dentro `pnpm test`;
  - eccezioni in sola lettura (D-059): le cartelle elencate in `.claude/read-allow.local`, fuori da git, si possono leggere con Read, Grep, Glob e con comandi Bash di sola lettura; scrivere resta bloccato, e la home intera non si può elencare. Solo per codice pubblico scelto dall'utente come riferimento, mai per cartelle con dati personali;
  - i test stanno in `.claude/hooks/block-outside-repo.test.js`; `.claude/hooks/package.json` tiene gli script in CommonJS anche se il monorepo è ESM.
- La protezione vera per i comandi di shell è la sandbox del sistema operativo: `node` e `pnpm` eseguono codice arbitrario, e l'hook guarda solo il testo del comando. Per lo sviluppo non è configurata nel repository: la attiva l'utente con `/sandbox` in Claude Code. Per gli esecutori lanciati da Arianna è il task 1.6.

## Servizi locali e database

- PostgreSQL ascolta solo su `127.0.0.1` e la configurazione rifiuta host diversi dal loopback, perché il driver non usa TLS.
- **Due ruoli (D-046).** Il proprietario dello schema (`database.user`) è superuser del cluster (così lo crea l'immagine Docker) e serve solo alle migrazioni e a impostare la password di `arianna_app`. Il core lavora come `arianna_app`, che legge e scrive righe ma non altera tabelle, non disattiva trigger, non cancella righe, non crea tabelle temporanee (che nelle funzioni dei trigger nasconderebbero le tabelle vere) e sulle tabelle append-only può solo inserire.
- **Cosa protegge e cosa no.** Una connessione rubata o un'iniezione SQL nel core non riscrivono la storia né aggirano i trigger di guardia. Chi esegue codice nel processo del core ha la password di `arianna_app` e niente di più solo se il core non conosce quella del proprietario: con le password vere `pnpm start` legge dal vault solo quella di `arianna_app` e non applica migrazioni (prima serve `pnpm db:migrate`); con quelle di sviluppo migra da solo. Chi ha la password del proprietario può manomettere il registro, e la manomissione resta rilevabile dalla catena. `UPDATE` su `tasks`, `approvals` e le altre tabelle di stato è concesso su tutte le colonne: decidono i trigger di guardia (permessi per colonna da valutare). `arianna_app` può cambiare la propria password (PostgreSQL lo consente a ogni ruolo): il danno è un blocco, non un'escalation, e `pnpm db:migrate` la reimposta. **Eccezione voluta (D-057):** `arianna_app` può chiamare `purge_conversation(uuid)`, che gira come il proprietario e cancella i testi di una conversazione archiviata senza task al lavoro (messaggi, passi, deleghe, titoli, testi delle schede), lasciando registro del gateway, decisioni del router, run, cambi di etichetta ed eventi. Poiché `arianna_app` può archiviare da sé ogni conversazione tranne quella di Telegram, chi controlla il core può cancellare i testi di tutte le altre conversazioni; non può riscrivere la storia né toccare il registro, e ogni cancellazione lascia l'evento `conversation.purged`. La funzione non prende blocchi di tabella né spegne trigger: i trigger append-only lasciano passare le sue cancellazioni solo quando chi esegue è il proprietario della tabella e la transazione porta l'impostazione `arianna.purge` (che `arianna_app` può scrivere, ma senza essere mai il proprietario fuori dalla funzione). Il doctor segnala ogni altra funzione che giri come il proprietario e che `arianna_app` possa eseguire, e controlla che `purge_conversation` non sia aperta a tutti e abbia il `search_path` fissato. **Limiti noti:** le versioni vecchie delle righe cancellate o svuotate restano nelle pagine del database e nel WAL finché PostgreSQL non riusa lo spazio (VACUUM, riciclo del WAL), e quindi anche nei backup fatti prima; l'impronta sha256 di un testo declassato resta in `label_changes` e `gateway_log` e può confermare un testo breve che qualcuno indovini.
- In sviluppo le password sono valori fissi (`arianna_dev` in `compose.yaml`, `arianna_dev` e `arianna_app_dev` nel codice): vanno bene solo finché il database contiene dati finti. **Prima dei dati veri** `pnpm arianna:doctor` deve passare: password dal vault, di almeno 24 caratteri e diverse; quelle di sviluppo rifiutate dal database; migrazioni applicate; limiti di `arianna_app`; catena degli eventi.
- **Passi per le password vere.** 1) Due segreti diversi nel vault con `pnpm vault:edit` (per esempio `db-owner-password` e `db-app-password`: ASCII stampabile senza spazi, almeno 24 caratteri casuali). 2) In `arianna.toml`, sezione `[database]`, `password = "vault://db-owner-password"` e `app_password = "vault://db-app-password"`. 3) La password del proprietario si cambia nel database con `docker compose -p arianna exec postgres psql -U arianna -d arianna` e poi `\password arianna`: psql chiede la password senza mostrarla e invia solo il verificatore, quindi non finisce né nella cronologia né nel log. Non usare `ALTER ROLE ... PASSWORD '...'`, che resta nella cronologia di psql. 4) `pnpm db:migrate`, che imposta quella di `arianna_app`. 5) `pnpm arianna:doctor`.
- `compose.yaml` contiene solo la password di sviluppo, che l'immagine legge quando crea `data/postgres`: una password vera nell'ambiente del container resterebbe leggibile con `docker inspect`. Per questo la si cambia dopo, con `\password`.
- La password di `arianna_app` si imposta inviando il verificatore SCRAM, non la password: un server che registra le istruzioni DDL non la scrive nel log.
- Il Coder lavora solo nei progetti che l'utente approva in `[[project]]` di `arianna.toml` (D-058): cartelle sotto la home (mai la home intera, cartelle nascoste, `Library`, Arianna o `data/`) o `repos/<nome>`, con etichetta L0 o L1. La lista la scrive solo l'utente: oggi l'API non ha autenticazione (1.13), quindi la chat può solo scegliere fra i progetti approvati, mai aggiungerne. Il link `repos/<nome>` è una scorciatoia; il percorso approvato si ricontrolla su disco a ogni lancio (nessun link sul percorso). Rischio residuo: fra il controllo e l'avvio di `claude` passano pochi istanti in cui chi scrive nella home potrebbe sostituire la cartella; `run.ts` ricontrolla il percorso subito prima dell'avvio, e chi può già scrivere nella home dell'utente non ha bisogno di Arianna per leggerla.
- Il Coder può lasciare nel progetto file di configurazione che altri strumenti eseguono quando l'utente apre la cartella con loro, fuori da ogni sandbox: `.claude/` (hook di Claude Code), `.mcp.json`, `.envrc` (direnv), `.vscode/`, `.idea/`, `.devcontainer/`, `.husky/`, `.githooks/`, `.pre-commit-config.yaml`, spesso ignorati da git. Arianna li confronta prima e dopo ogni run (`toolConfigFiles`) e li nomina nel risultato che legge, con l'avviso di controllarli prima di aprire la cartella con quegli strumenti: non li blocca né li annulla. Rischio residuo: un file di configurazione di un altro strumento, fuori da quella lista, resta visibile solo se git lo mostra.
- Nei progetti il Coder lavora nella cartella del progetto stessa, sul branch corrente (D-056, scelta dell'utente): vede ciò che vede Claude Code lanciato dall'utente lì, compresi i file ignorati da git; la sandbox gli nega la rete e ogni lettura fuori da quella cartella, la scansione preventiva ferma segreti tracciati o non ignorati (repository annidati e sottomoduli bloccano), e con modifiche non committate il lancio aspetta l'approvazione dell'utente. La `.git` di quella cartella è scrivibile dal Coder: i comandi git di Arianna lì girano con ambiente minimo, senza hook né filtri (mai `git status`), e un'impronta della configurazione git presa prima del run ferma tutto se è cambiata dopo; i comandi git dell'utente restano esposti a ciò che il Coder lascia in `.git`, come con la CLI. La copia di lavoro, quando si usa (eval, fuori allowlist), non è un `git worktree`: altrimenti potrebbe leggere tutta la storia del repository d'origine (segreti cancellati compresi) e scrivere nella sua `.git` (hook, `core.fsmonitor`, filtri) codice eseguito poi fuori dalla sandbox. È un repository nuovo con un solo commit, scritto senza filtri né hook (D-041).
- Un esecutore cloud gira sulla stessa macchina e può raggiungere via loopback il database, Qdrant e il modello locale: sarebbe un percorso L2 verso il cloud che non passa dal gateway. La sandbox del task 1.6 deve negare queste connessioni, e il test del canarino lo verifica.
- Il campo `detail` degli errori di PostgreSQL contiene la riga rifiutata, payload compreso: non va scritto nei log per eventi L2 o superiori.

## Vault

- Primo avvio, a mano: `age-keygen -o <file>` nella posizione dove `sops` cerca la chiave (su macOS `~/Library/Application Support/sops/age/keys.txt`, oppure un file indicato da `SOPS_AGE_KEY_FILE`), poi `pnpm vault:init <chiave pubblica age1...>` e `pnpm vault:edit`. Le chiavi del file sono di primo livello: `nome: valore`, letto come `vault://nome`.
- La chiave privata non entra mai in `ARIANNA_HOME`, in git o nella cartella sincronizzata: senza di lei `data/vault/secrets.yaml` è illeggibile, e perderla vuol dire perdere i segreti. Va conservata a parte (per esempio nel gestore di password).
- Il controllo del gateway confronta valori esatti: un segreto trasformato (in base64, spezzato fra frammenti dello stesso payload, abbreviato) non si riconosce, e il registro dei valori rivelati si svuota a ogni riavvio del processo (D-043). È una rete, non il controllo principale, che resta non mettere mai il valore in un testo.

## Telegram

- **Spento per ora (D-110, domanda 12, scelta dell'utente del 2026-10-05):** dal telefono si usa la chat web come app via VPN (task 1.19). Il codice resta e le regole sotto valgono se l'utente lo riaccende.
- Telegram è un canale cloud (D-016): riceve al massimo L1, solo attraverso il gateway, e un contenuto sopra L1 diventa un rimando alla chat web. Il client del Bot API (`apps/core/src/telegram/api.ts`) accetta solo testi usciti da una decisione `allow` verso `channel:telegram`.
- In sviluppo nessun bot vero né token reale: i test usano un finto Bot API su loopback (D-044).
- Per l'uso vero (dopo il criterio della Fase 1A): creare il bot con BotFather, mettere il token nel vault con `pnpm vault:edit` alla chiave `telegram-bot-token`, scrivere in `arianna.toml` la sezione `[telegram]` con `token = "vault://telegram-bot-token"` e l'id della propria chat privata in `chats`. Il token non va mai in `arianna.toml`: la configurazione accetta solo un riferimento `vault://`.
- Il bot ascolta con long polling: nessuna porta esposta. Risponde solo alle chat private elencate in `chats`, scritte dal loro stesso utente; il resto è ignorato. Cambiare `chats` è un'impostazione di privacy: solo l'utente la modifica.
- Il token compare solo nel percorso delle richieste a `api.telegram.org`, con un agent proprio che non usa proxy né segue redirect; gli errori riportano metodo e stato HTTP, mai URL o corpo.
- Un'approvazione su Telegram mostra solo l'azione e, se il task è al massimo L1, il suo titolo: il dettaglio si legge nella chat web. I declassamenti si decidono solo dal web.
- Chi ha il telefono sbloccato con Telegram aperto può approvare: proteggere l'app con un codice è una buona pratica (da ricordare nel wizard, task 1.18).
