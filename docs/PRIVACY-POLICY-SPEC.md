# Specifica della policy di privacy

## Livelli

| Livello | Significato | Esempi | Chi può leggerlo |
| --- | --- | --- | --- |
| L0 | Pubblico | Documentazione open source, pagine web | Qualsiasi esecutore |
| L1 | Interno | Codice proprio non sensibile, appunti di lavoro | Locale e cloud, con log |
| L2 | Privato | Fatture, contratti, documenti personali, codice di clienti sotto NDA | Solo modelli locali |
| L3 | Segreto | Credenziali, chiavi, codici | Nessun modello: solo riferimenti al vault |

## Regole

1. **Default-deny:** un dato senza etichetta è L2.
2. **Contaminazione di sessione:** un agente che legge L2 resta locale per tutta la sessione; il router lo impone.
3. **Etichette solo verso l'alto:** abbassare un'etichetta richiede approvazione esplicita dell'utente, registrata in `label_changes`.
4. **Gateway unico:** tutto ciò che esce dalla macchina passa da `packages/policy`; il gateway blocca L2/L3 (eccetto l'indirizzo di un link verso il suo sito, con il consenso dell'utente e le regole della destinazione `link`, D-154, e, dopo un accesso fatto dall'utente nel browser dell'agente, le richieste di quel sito e i moduli dell'utente verso di esso, destinazioni `web-session` e `web-form`, mai L3, D-276; dalla chat Privata in cui passa il browser dopo l'accesso, anche il testo scritto in un campo di quel sito, `web-typed-session`, e solo da un contesto che ha letto L2 soltanto da quel sito e dall'utente, D-281) e registra ogni uscita (cosa, verso chi, perché). "Uscita" significa tutte e cinque le superfici elencate sotto, non solo il prompt.
5. **Codice di clienti con NDA:** L2 finché i contratti non sono stati letti.
6. **Segreti (L3):** mai nel prompt; solo riferimenti (`vault://nome`) risolti dal processo che li usa. Gestione con `sops` + `age` in `@arianna/vault` (D-042): il valore esce solo con `reveal()` e, stampato o serializzato, resta il riferimento. Ogni valore rivelato nel processo è noto al gateway, che blocca con la regola `secret` qualsiasi uscita che lo contiene, verso il modello locale e la chat web compresi; lo stesso controllo vale per i frammenti della risposta in streaming, uniti a quelli già inviati (D-043). I valori sotto 8 caratteri non si cercano, e il registro dei valori rivelati vale per il processo: dopo un riavvio un valore è noto di nuovo quando viene risolto.
7. **Voce:** la chiamata via internet (browser sul Mac o dal telefono attraverso la VPN dell'utente) è un canale locale: riconoscimento e sintesi girano sul Mac e può dire L2. La telefonia vera aggiunge un percorso audio nel cloud (operatore e servizio SIP): vale la regola 10, al massimo L1 e un rimando alla chat, senza abilitazioni per chiamata (scelta dell'utente del 2026-10-05, D-110 domanda 5: chi scrive la frase non cambia dove passa l'audio).
8. **Taint (D-015):** l'output di un modello ha l'etichetta più alta fra i suoi input. Un riassunto, un piano o un brief scritto da un modello che ha letto L2 è L2, anche se "sembra" innocuo.
9. **Clearance (D-015):** ogni conversazione, task e run ha un tetto (`clearance`) e un'etichetta effettiva (`effective_label`, il massimo di ciò che ha letto davvero). Una lettura sopra il tetto è negata, non contamina. Un esecutore cloud è ammesso solo se `effective_label ≤ L1`.
10. **Canali esterni (D-016):** Telegram e telefono sono destinazioni cloud come Claude Code (Telegram è spento per ora, D-110; la regola vale se torna). Ricevono al massimo L1; un contenuto L2 diventa una notifica con riferimento ("hai una carta in attesa, apri la chat web"). Solo la chat web raggiunta via VPN, chiamata via internet compresa, è un canale locale.
11. **Confinamento degli esecutori cloud (D-014):** un processo `claude` o `codex` vede solo la propria cartella di lavoro, in un progetto approvato (D-058), con il profilo descritto sotto.
12. **Log:** eventi e log con etichetta L2 contengono riferimenti (id, percorso, hash), mai il contenuto.

## Le cinque superfici d'uscita

Il controllo sul solo prompt non basta: un esecutore cloud apre i file da sé e chiama strumenti. Il gateway copre:

| Superficie | Rischio | Controllo |
| --- | --- | --- |
| Prompt e allegati verso un esecutore cloud | Frammento L2 nel testo | `gatewayCheck` sulle etichette + scanner deterministico |
| File che l'esecutore cloud può leggere | Legge fuori dal compito (home, `data/`, altri repository) | Confinamento: worktree, allowlist, sandbox, scansione preventiva |
| Strumenti MCP chiamati da una sessione cloud | `kb.read` restituisce una pagina L2 | Il server MCP conosce la clearance della sessione e nega sopra L1 |
| Canali esterni (telefono, Telegram se torna, più avanti mail) | Arianna scrive un importo o un nome su Telegram | Stesso `gatewayCheck`, destinazione `channel` |
| Ricerche web da agenti locali | La query contiene dati L2 | Una sessione con `effective_label ≥ L2` non ha strumenti web |

**Terminale del Coder nella chat (D-095, tappa 1):** comandi `Bash` e uscite di un run di `claude -p` vanno alla chat web (notifica `terminal` su `pg_notify`) e si salvano con la loro delega in `task_terminal` (migrazione `0062`, scelta dell'utente del 2026-10-14 durante la prova; mai per una conversazione in incognito, cancellati con la conversazione), mai mandati a un canale esterno (Telegram prende solo gli eventi); tagliati a 200 righe o 16 KiB per comando, con le righe che contengono un valore del vault già rivelato sostituite (un valore spezzato fra righe nasconde tutto il testo); solo per progetti fino a L1, con l'etichetta del progetto (o del brief, se più alta), e solo se la clearance del task, che sta dentro quella della conversazione, la raggiunge. I segreti di un `.env` del progetto non sono noti al vault e restano visibili a schermo e salvati nel database locale, quindi anche nei suoi backup (D-096): rischio accettato dall'utente con D-095, a schermo nella prima scelta e salvato nella risposta del 2026-10-14, la cui opzione lo diceva («un .env letto dal Coder resterebbe nel database locale»).

## Conversazioni: lavoro e privato

Il nodo più delicato è l'orchestratore: è locale, legge L2 e scrive i brief per gli agenti cloud. Senza una regola, ogni brief sarebbe contaminato (regola 8) oppure porterebbe fuori dati privati.

- **Conversazione di lavoro** (`mode = work`, clearance L1): legata a un progetto approvato (D-058). L'orchestratore non può leggere L2 (la ricerca in KB privata è negata con un messaggio che invita ad aprire una conversazione privata). I brief nascono L1 ed escono senza approvazione.
- **Conversazione privata** (`mode = private`, clearance L2, predefinita): tutto resta locale. Se serve un esecutore cloud, il brief esatto ti viene mostrato in una scheda di approvazione ("esce verso Claude Code: …"); approvando lo declassifichi a L1 (regola 3) e solo quel testo esce.
- Il contesto dell'orchestratore è **per task**, non una sessione unica e lunga: un task L1 non eredita il contesto di una conversazione privata.
- **«@nome» e «/giro»** (D-219): il testo dopo il nome o il comando è il brief, con l'etichetta del task (almeno quella del messaggio); il core scrive la delega passando da `delegateCall` come per una delega di Arianna, quindi in una conversazione privata verso il cloud esce solo il testo esatto che l'utente approva (regola 3), e valgono gateway, secondo controllo dei dati personali e segno Finanze. `tasks.addressed_agents` tiene solo nomi di agenti (vincolo nel database), mai testo. **«Ha visto solo il brief»** rimostra quel testo nella pagina della sua conversazione: solo una conversazione con Arianna non cancellata, solo entro la clearance della conversazione, passando dal gateway verso la chat web (registrato in `gateway_log`); mai per id da un'altra conversazione.
- **«/progetta» e piani modificabili** (D-235): la carta «Piano» porta il testo dell'utente con l'etichetta del messaggio; pianifica Claude solo in una conversazione di lavoro entro L1, passando dal gateway come `task.plan` (D-164), altrimenti il modello locale, sempre in una privata, qualunque cosa dica `planner` del progetto. Le modifiche al piano fatte nella sua scheda restano all'etichetta della conversazione (non L2 come le carte scritte sul cardwall); in una conversazione di lavoro passano dallo stesso scanner dei messaggi e un testo che lo alzerebbe sopra L1 è rifiutato.
- **Chat letta dagli specialisti locali** (D-220): un agente che risponde sul modello locale senza strumenti legge, oltre al brief, la finestra della conversazione che legge Arianna (riassunto ancorato e messaggi fino a quello che ha aperto il task, con i rapporti degli altri agenti), solo in una conversazione con Arianna e solo se la clearance della conversazione non supera quella dell'agente e del task: un agente dell'utente (al massimo L1) la legge in una conversazione di lavoro, mai in una privata, nemmeno dopo un declassamento del brief. Nulla esce dal Mac; ogni messaggio passa dal gateway con la sua etichetta e conta nell'etichetta del rapporto. Un agente cloud riceve sempre solo il brief.
- **Chat diretta con un agente** (D-111d): vale quello che segue per il Coder per ogni agente su Claude; un agente locale risponde con il modello locale, quindi nulla esce dal Mac, e una conversazione privata con lui è ammessa solo se la sua scheda può leggere Privato (altrimenti il brief chiederebbe un declassamento). Modo e progetto li decide la scheda, nel codice; il database ammette solo un id di agente diverso da Arianna in una conversazione dell'utente.
- **Chat diretta con il Coder** (D-111, `conversations.agent = 'coder'`): una conversazione di lavoro (L1) su un progetto approvato in cui l'orchestratore non c'è. Ogni messaggio dell'utente è il brief, così com'è: scanner al salvataggio come in ogni conversazione di lavoro, poi gateway verso `claude` a ogni messaggio; il modello locale non legge e non scrive nulla. Si sceglie alla nascita e non cambia (trigger `conversations_agent_fixed`): una storia scritta per Arianna non passa mai al cloud. L'utente vede un avviso fisso alla creazione, il segno "va a Claude" nell'intestazione e una conferma oltre 4000 caratteri (lo scanner non riconosce i dati personali in prosa). **La sessione cloud è per conversazione:** dal secondo messaggio il run riprende con `--resume` la sessione dell'ultima risposta della stessa conversazione, stesso agente e progetto, e ha quindi letto i messaggi precedenti, le sue risposte e i file aperti prima. È accettabile perché quella sessione resta L1 (nessun declassamento possibile in una conversazione di lavoro), su un solo progetto, ogni testo entrato ha la sua riga in `gateway_log` e nessun pezzo di Arianna o di altre conversazioni vi entra; un messaggio bloccato dal gateway non entra mai. Se la sessione non c'è più, il ripiego rimanda dal gateway gli ultimi scambi con una risposta, ciascuno con la sua etichetta (D-111b). Claude Code tiene una copia della sessione nella home dell'utente: eliminare la conversazione in Arianna non la cancella, e la finestra di eliminazione lo dice.
- **«Con chi parli»** (D-111 tappa B, D-209): una conversazione nasce anche con il **modello locale** (`conversations.agent = 'local-chat'`), solo privata (L2): la scheda `local-chat` ha solo `kb.search` e `kb.read`, che leggono fino alla clearance della conversazione (mai L3), nessuna uscita (niente `kb.write`, carte, deleghe, canali), e Arianna non le delega mai; oppure con **Claude senza progetto** (`agent = 'claude'`), solo di lavoro (L1): la catena della chat di sistema di D-064, senza strumenti, con un prompt fisso nostro (L0), in una cartella vuota della conversazione (`data/worktrees/chat-<id>`) dove nessun file dell'utente entra. Come nella chat diretta, il messaggio è L1 per il modo, lo scanner lo rifiuta al salvataggio se trova IBAN, codici fiscali, carte o chiavi, e il gateway lo controlla di nuovo all'uscita; dal secondo messaggio esce solo il messaggio nuovo (sessione ripresa con `--resume`), e se la sessione non c'è più passano di nuovo dal gateway gli scambi a cui Claude ha risposto (al più 10 e 12 000 caratteri, i più recenti), mai un messaggio bloccato dal gateway o senza risposta, come il ripiego del Coder (D-111b). Una conversazione privata non ha mai un interlocutore cloud: lo vietano il codice e i vincoli della migrazione `0063`; con Claude spento risponde nessuno, mai il modello locale al suo posto. La copia della sessione di Claude Code nella home resta anche qui. **ChatGPT senza progetto** (`agent = 'codex'`, D-212) segue le stesse regole sulla stessa catena, verso `codex` con il profilo di D-138 senza eccezioni: prompt fisso nostro (L0), la stessa cartella della conversazione, che per Codex è un repository git vuoto aperto in **sola lettura**; Codex non ha un elenco di strumenti da chiudere, quindi la shell resta, ma in una cartella vuota, senza rete e con `ARIANNA_HOME` e la home negate, e il run si ferma dopo 2 comandi senza risposta. Con Codex spento non risponde nessuno, mai Claude né il modello locale al suo posto; la copia della sessione di Codex nella home resta come per le deleghe. Delle chat semplici il database tiene solo quanto è piena la sessione dopo ogni risposta (`runs.context_tokens`, un numero), per l'indicatore del contesto.
- **Immagini e file allegati** (D-247): ogni allegato è **L2**, sempre, e si lega solo a un messaggio di una conversazione privata dell'utente con Arianna o con il modello locale (mai di lavoro, incognita, della segretaria, a lato, di sistema o diretta con un agente; lo controllano il core e il database, migrazione `0075`). I byte stanno in `data/attachments` e vanno solo a oMLX su questo Mac: un'immagine la legge il modello del ruolo `vision` (Qwen3.5 9B), dopo un passaggio dal gateway verso `local` con il prompt (L0) e un segno con l'impronta dell'immagine (L2); la sua lettura e il testo di un file allegato entrano nella storia dell'orchestratore come parti L2, che il gateway non lascia uscire. Un brief verso il cloud scritto dopo averli letti segue la regola della conversazione privata: esce solo il testo esatto che l'utente approva.

### Conversazioni incognite (D-136)

Un'incognita è una conversazione privata o di lavoro con un segno fissato alla nascita (`conversations.incognito`, immutabile). **Non cambia nessuna etichetta né uscita:** clearance, scanner, gateway, approvazioni e declassamenti funzionano come nella conversazione corrispondente; il segno dice **quanto a lungo** si tiene un dato, non quanto è riservato, e `packages/policy` non lo conosce. Cambia la durata: alla chiusura ("Termina", 10 minuti senza pagina aperta, riavvio del core) il lavoro in corso si ferma e `purge_incognito` cancella i testi.

| Traccia | Esito |
| --- | --- |
| Messaggi, turni e ragionamento, deleghe (brief e rapporti), riassunti, righe di attività, partecipanti | Cancellati alla chiusura |
| Titolo della conversazione e dei task | Mai scritti (`NULL` e "Incognito" fisso) |
| Note in `kb/inbox/`, carte figlie (`kb.write`, `task.create`, `task.update`, "Salva in inbox", `/nota`) | Mai scritte: strumenti spenti, rotte 409 |
| Sessioni di Claude Code nella home dell'utente | Non salvate (`--no-session-persistence`); altre cartelle del profilo da verificare dal vivo (eval dal vivo in sospeso, domanda in `OPEN-QUESTIONS.md`); la scheda lo dice |
| Appunti del sistema dopo "Copia" | Fuori dal controllo di Arianna (un gestore degli appunti può conservarli): la scheda lo dice |
| Telegram, chiamate (in entrata, in uscita, programmate), notifiche | Saltate; le chiamate legate a un'incognita sono rifiutate e la chiusura annulla quelle rimaste |
| `events`, `gateway_log`, `router_decisions`, `runs` (senza `session_ref` né cartella), `label_changes`, `task_errors`, `jobs`, riga scheletro della conversazione e dei task | Restano, senza contenuto: dicono se e verso chi qualcosa è uscito, mai cosa. Restano anche due **impronte** sha256 (`gateway_log.payload_sha256` di ogni uscita e `label_changes.subject` di un declassamento): non contengono il testo, ma permettono di confermare un testo breve indovinato |
| Testo esatto uscito (`gateway_texts`, D-297) | Mai scritto per un'incognita |
| Ciò che il fornitore cloud ha ricevuto (solo incognite di lavoro) | Resta presso il fornitore, secondo l'abbonamento |
| File cambiati dal Coder nel progetto | Restano: elencati nella scheda di chiusura |
| Byte cancellati nelle pagine del database, nel WAL e nella coda di `pg_notify` | Restano illeggibili ad Arianna fino alla sovrascrittura; li protegge la cifratura del disco |
| Log di oMLX | Senza testi al livello `info`, che il wizard scrive e il doctor pretende, in `data/omlx/logs` con `--base-path data/omlx` (D-221); la cache su SSD (se accesa) tiene blocchi derivati dai prompt fino allo sfratto |

L'utente vede questo elenco prima del primo messaggio e di nuovo alla chiusura, con i numeri veri di quella conversazione. Una memoria a lungo termine (Fase 2) dovrà escludere le incognite.

### Eliminazione per sempre (D-157)
 **Limiti noti (revisione del 2026-10-10):** restano le righe del gateway delle chiamate vocali, che non portano il task (ora, etichetta e impronta sha256 di ciò che è stato detto, senza testo), e quelle dei link scaricati (`target_kind = 'link'`, impronta dell'indirizzo), che non appartengono a una conversazione; la ricucitura riscrive ogni evento successivo al primo tolto tenendo il lock della catena, quindi eliminare una conversazione vecchia ferma per qualche istante la scrittura degli eventi. **Difese:** l'eliminazione è rifiutata (55000) se un id delle sue righe è anche l'id di una riga di un'altra tabella (un id falsificato dal core porterebbe via gli eventi di quella riga); una chiamata viva la rifiuta prima di fermare i passi; un rifiuto dopo lo stop rimette in coda i passi fermati, così nulla cambia; le cartelle `data/worktrees/<runId>` dei run eliminati si cancellano.
Scelta dell'utente del 2026-10-10, che supera D-046 e D-057 in questo punto. **"Elimina"** di una conversazione (dalla lista, dalle chat di sistema o dalle Archiviate, con la conferma "Eliminare per sempre?") toglie dal database tutto ciò che la conversazione ha lasciato, **registro compreso**: messaggi, task, passi, deleghe e loro file, chiamate, attività, riassunti, partecipanti, errori, approvazioni, decisioni del router, righe del gateway (anche il riassunto L1 di ciò che è uscito e, con le righe, il testo esatto uscito di D-297), cambi di etichetta ed eventi della conversazione e dei suoi task, e le chat di sistema sui suoi task. La catena degli eventi si ricuce (impronte ricalcolate dalla prima riga tolta) e resta una sola riga `events.rewoven` senza contenuto. Restano: le card create da lì (senza il legame), le note salvate nella Conoscenza, i file cambiati dal Coder nei progetti, ciò che un fornitore cloud ha già ricevuto, le sessioni di Claude Code e Codex nella home dell'utente, i byte nel database fino alla sovrascrittura (come sopra). Mai la conversazione della segretaria, quella di Telegram né un'incognita aperta (ha "Termina"). **Note:** "Elimina" nella pagina di una nota della Conoscenza, nei Pensieri e nella scheda "Conoscenza" di un progetto cancella il file dal disco, solo per un clic dell'utente nella chat (nessuno strumento di Arianna elimina note); l'evento `note.deleted` dice solo dove (`inbox`, `kb`, `project`), mai percorso né titolo. Nessuna regola nuova in `packages/policy`: l'eliminazione non fa uscire nulla.

## Confinamento degli esecutori cloud

Profilo applicato da `packages/executors` a ogni lancio; i nomi esatti dei flag si verificano su `claude --help` e `codex --help` nei task 1.5 e 1.16 e si fissano nel test di contratto (per `codex` 0.160.0, D-138).

1. **Progetti approvati (D-058, prima `allowlist`):** il Coder lavora solo in una cartella elencata dall'utente nelle sezioni `[[project]]` di `arianna.toml` (nome, percorso, etichetta L0 o L1, predefinita L1). Il percorso è `~/...` sotto la home dell'utente oppure `repos/<nome>` dentro `ARIANNA_HOME`: mai la home stessa, cartelle nascoste (`.ssh`, `.config`...), `Library`, `ARIANNA_HOME` né cartelle dentro o attorno ad essa (salvo `repos/<nome>`), mai un progetto dentro un altro (anche per maiuscole). Cambiare la lista è un'impostazione di privacy: la scrive solo l'utente (wizard o a mano), mai un agente; il core la rilegge senza riavvio, e un progetto tolto chiude la delega al passo successivo. L'etichetta del progetto vale per tutti i suoi file: `labels.toml` non serve per i progetti. Una vecchia `[cloud] allowlist` non vuota è rifiutata con l'indicazione di passare ai `[[project]]`, mai convertita da sola. Una conversazione di lavoro nomina un progetto approvato per nome (in `conversations.workspace`; le conversazioni precedenti con `repos/<nome>` valgono come il progetto `<nome>`). Il link `repos/<nome>` che il wizard crea per un progetto sotto la home è solo una scorciatoia dell'utente: il Coder usa sempre il percorso approvato.
2. **Cartella di lavoro.** Per un progetto approvato il Coder lavora **nella cartella del progetto stessa** (D-056, scelta dell'utente: "come con la CLI di Claude Code"), sul branch corrente, senza copia: `openRepository` in `packages/executors` controlla a ogni lancio che il percorso approvato sia esattamente se stesso su disco (`realpath`: nessun link lungo il percorso, così un link cambiato dopo l'approvazione non sposta il Coder), che non contenga `ARIANNA_HOME` e vi stia dentro solo come `repos/<nome>`, e che sia la radice di un repository git; scansiona con `checkProject` (l'etichetta del progetto) i file tracciati e quelli non ignorati da git (un `.env` ignorato non blocca: l'utente lo mostra già a Claude Code quando lo lancia lui), e con modifiche non committate chiede l'approvazione `workspace` dalla chat (legata ai file che nomina: un file sporcato dopo il sì viene richiesto). **Rischi residui accettati con D-056, ridotti da D-174:** nella cartella vera la `.git` (storia, configurazione, hook) è leggibile dal Coder; dal D-174 è in **sola lettura** per Claude (`denyWrite` della sandbox per Bash, regola `permissions.deny` `Edit(//…/.git/**)` per gli strumenti dei file) come già per Codex, e gli agenti non fanno commit: lo prova il canarino dal vivo `--tag git` (commit, cambio di ramo, `.git`/`.GIT`/collegamento con Bash e con gli strumenti dei file: HEAD e rami invariati, nessun file creato). Restano: un repository annidato creato durante il run (`git init sub`, la sua `.git` non è protetta; il lancio successivo si blocca, ma un comando git dell'utente in `sub/` eseguirebbe ciò che c'è); per questo ogni comando git di Arianna in quella cartella gira con un ambiente minimo (nessun segreto del core), senza hook, fsmonitor, configurazione globale né lock facoltativi, e usa solo comandi che non convertono contenuti attraverso i filtri (`ls-files`, `diff-index --cached`, mai `git status`); un'impronta di `.git`, `.git/config`, hook, `info/attributes` e di ogni `.gitattributes` è presa prima del run e confrontata dopo: se cambia, la delega fallisce con un messaggio esplicito e nessun comando git di Arianna gira lì finché l'utente non ha guardato. I comandi git dell'utente, invece, eseguono ciò che il Coder ha lasciato in `.git`: è la stessa esposizione dell'uso diretto della CLI. Un repository annidato o un sottomodulo è una voce speciale che blocca il lancio (i loro file non sono scansionati); un link simbolico ignorato da git non è scansionato. La **copia dedicata** per run, in `data/worktrees/<run>` (`prepareWorkspace`), resta per gli eval e per usi fuori allowlist: non un `git worktree`, il cui file `.git` porterebbe l'esecutore a tutta la storia del repository d'origine (segreti cancellati compresi) e alla sua cartella `.git` scrivibile (hook e configurazione eseguiti poi fuori dalla sandbox). I file di un commit si scrivono così come sono nel database degli oggetti (`git ls-tree` e `git cat-file`: nessun filtro, hook o fsmonitor eseguito; senza configurazione globale o di sistema; percorsi con `..` o `.git` e file sotto un collegamento simbolico rifiutati; sottomoduli non estratti), poi si crea lì un repository nuovo con un solo commit, perché l'esecutore possa fare diff. Il repository in allowlist dev'essere una cartella vera, non un collegamento simbolico. La directory di lavoro del processo è quella cartella; se la scansione blocca, viene rimossa subito. Riportare le modifiche nel repository d'origine spetta al chiamante (1.10). Quando Claude risponde a una chat di sistema (D-064, seconda parte) non lavora su un progetto: `prepareEmptyWorkspace` gli dà una cartella vuota `data/worktrees/<run>`, senza scansione perché non ha file, tolta dopo il run (e quella di un run interrotto alla ripresa); niente strumenti, e il brief è la chat passata dal gateway. **Parti e note di un contenitore (D-145, D-166):** per una parte di un progetto contenitore la cartella di lavoro è la parte; il contenitore è negato intero dalla sandbox (`denyRead` per `claude`, voce `deny` per `codex`) e la parte riaperta, così le cartelle di gestione accanto non si leggono, nemmeno con la shell. Le note delle cartelle di gestione al massimo L1 (`checkCoderNote` in `packages/policy`: niente link, file di istruzioni di un agente, percorsi non semplici, nomi da segreti) passano **una per una dal gateway** verso l'esecutore del run e arrivano come copia di sola lettura in `data/worktrees/<run>.notes`, con il testo esatto lasciato uscire (`prepareProjectNotes`, che spende la decisione); la copia è leggibile dalla sandbox e, per `claude`, dagli strumenti di file con `--add-dir`; si toglie a fine passo. Le note sopra L1, quelle che il gateway ferma e ogni altro file del contenitore non sono mai nella copia.
3. **Scansione preventiva** (`checkWorkspace` in `packages/policy`, pura; la lettura del disco è `scanWorkspace` per la copia, `openRepository` per la cartella del progetto, che salta i file ignorati da git): il lancio è negato se la cartella di lavoro contiene file sopra L1 secondo le regole per cartella applicate al percorso nel repository d'origine (non a `data/worktrees`, che è L2), file di segreti, anche quando il nome da segreto è una cartella del percorso (`.env`, `.env.*`, `*.env`, `.envrc`, `.netrc`, `.npmrc`, `.pgpass`, `.pypirc`, `.htpasswd`, `.dockercfg`, `.git-credentials`, `credentials`, `credentials.json`, `terraform.tfstate`; `*.pem`, `*.key`, `*.p8`, `*.p12`, `*.pfx`, `*.age`, `*.jks`, `*.keystore`, `*.kdbx`, `*.gpg`, `*.tfvars`, `*.tfstate`; chiavi SSH private `id_rsa*`, `id_dsa*`, `id_ecdsa*`, `id_ed25519*` tranne `.pub`; cartelle `.ssh`, `.gnupg`, `.aws`, `.kube`, `.docker`; nomi confrontati senza maiuscole), collegamenti simbolici con bersaglio assoluto, che escono dalla cartella anche solo per un passo o non si risolvono (quelli interni valgono per il loro bersaglio), file speciali o percorsi malformati. Il contenuto dei file non si legge: i dati finti dei test (IBAN di prova) bloccherebbero ogni repository.
4. **Permessi:** elenco chiuso di strumenti (`--tools` e `--allowedTools`), modalità non interattiva che nega ciò che non è in elenco (`--permission-mode dontAsk`, `--permission-prompts none`). Per `claude` (D-049) l'elenco ammesso è `Read`, `Glob`, `Grep`, `Edit`, `Write`: `Bash`, `WebFetch` e `WebSearch` solo dopo la sandbox (punto 6). Per `codex` (D-138) non c'è un elenco di strumenti: shell e modifiche dei file passano tutte dalla sandbox, e l'accesso è `read` o `write` sulla cartella di lavoro; `approval_policy="never"` fa fallire ciò che la sandbox rifiuta, `web_search="disabled"`; il run si ferma se lo stream mostra un elemento fuori dall'elenco chiuso (una chiamata MCP, una ricerca web, un sotto-agente).
5. **Nessuna configurazione ereditata:** solo i server MCP di Arianna (`--mcp-config` con `--strict-mcp-config`), senza impostazioni, hook o connettori del tuo profilo utente. Un `claude -p` che eredita i tuoi connettori personali (posta, drive) sarebbe una fuga. Per `claude` (D-049): `--mcp-config` vuoto, salvo le deleghe del Coder con strumenti di Arianna (D-261: solo il server `arianna`, da un file 0600 col token del run, e in quei soli run `--safe-mode`, che scarterebbe il server, è sostituito da sorgenti di impostazioni vuote, hook e memoria spenti e dalle variabili elencate in D-261, con l'`init` che deve mostrare solo il server `arianna` connesso, gli strumenti attesi, gli agenti incorporati e lo stile predefinito), `--restricted`, `--safe-mode` (negli altri run), `--disable-slash-commands`, `--no-chrome`; in uscita `--output-format stream-json --verbose` più `--include-partial-messages` (D-249: il testo e il pensiero mentre si scrivono, letti come `stream_event` e mostrati solo nella chat locale, filtrati come le righe di attività; nessuna capacità nuova per il modello); il messaggio `init` del binario si confronta con il profilo (strumenti, MCP, skill, plugin solo incorporati, abbonamento e non API key; nei run con il server MCP anche agenti solo incorporati e sempre elencati, stile `default`, nessun errore di plugin o di server) e il run si ferma se non torna. Per `codex` (D-138): `--ignore-user-config` e `--ignore-rules` (niente `config.toml` dell'utente: server MCP, connettori, profili, fiducia nei progetti; per questo nemmeno il `.codex/config.toml` di un progetto viene caricato), `--strict-config` (una chiave sconosciuta ferma il lancio) e venti funzioni spente con `--disable` (connettori, browser, computer use, generazione di immagini, plugin, hook, memorie, sotto-agenti, snapshot della shell di login…); niente file di istruzioni né skill nel prompt (`project_doc_max_bytes=0`, `skills.include_instructions=false`, `skills.bundled.enabled=false`), e finché esiste un `AGENTS.md` globale dell'utente nella cartella di Codex, che nessuna opzione spegne, il lancio è rifiutato. Codex non ha un messaggio `init`: l'allarme è l'elenco chiuso degli elementi dello stream.
6. **Sandbox del sistema operativo:** letture negate fuori dal worktree e dalla toolchain, rete limitata al fornitore del modello e ai registri dei pacchetti. Negate anche le connessioni via loopback ai servizi di Arianna (database, Qdrant, modello locale), che altrimenti sarebbero un'uscita L2 senza gateway; resta ammesso solo il server MCP di Arianna. Per `claude` (D-050): sandbox nativa di Claude Code passata con `--settings`, senza rete né loopback, senza tentativi fuori sandbox; letture negate nelle cartelle utente, in `ARIANNA_HOME` e nelle cartelle temporanee condivise, riaperte solo per worktree, `bin`/`lib` di Node e la cartella temporanea del binario; restano leggibili le cartelle di sistema (`/usr`, `/etc`, `/opt`…). Scritture solo nella cartella di lavoro, mai nella sua `.git` (D-174: `denyWrite` per Bash, `permissions.deny` per gli strumenti dei file). `Bash` ammesso solo con essa. Il server MCP di Arianna (D-261) non passa dalla sandbox dei comandi: ci parla il processo `claude`, su un listener a parte del core in `127.0.0.1` con un token per run, e ogni risposta esce dal gateway (clearance al più L1, rifiuti con testo fisso, tetti per run); i comandi di `Bash` restano senza loopback. Per `codex` (D-138): un profilo di permessi `arianna` passato con `-c`: `:minimal` in lettura (le cartelle di sistema; non le cartelle utente, `/opt` né `/Library`), in lettura la toolchain (Node del core, `bin`, `opt`, `Cellar`, `Caskroom` e `lib` di Homebrew ma non `var`, gli strumenti da riga di comando di Xcode, la cartella del binario), negate `ARIANNA_HOME`, `/tmp` e la cartella temporanea, la cartella di lavoro in lettura o in scrittura, con la sua `.git` in sola lettura; vince la regola più stretta. Senza tabella di rete: nessuna rete né loopback. Niente shell di login (i file della shell dell'utente restano chiusi).
7. **Ambiente pulito:** nessuna variabile con segreti ereditata. Arianna non legge mai l'archivio delle credenziali dei binari. Per `claude` (D-049) passano solo `PATH`, `HOME`, `USER`, `LOGNAME`, `TMPDIR`, più `LANG` e `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, e nei soli run con il server MCP di Arianna le variabili che spengono il profilo elencate in D-261; il prompt va su stdin, non fra gli argomenti visibili con `ps`. Per `codex` (D-138) passano solo `PATH`, `HOME`, `USER`, `LOGNAME`, `TMPDIR` e `LANG` (mai `OPENAI_API_KEY`, che userebbe un conto API, né `CODEX_HOME`); i comandi della shell ricevono le sole variabili di base, più `GIT_CONFIG_GLOBAL=/dev/null` e `GIT_CONFIG_NOSYSTEM=1`; il prompt va su stdin; niente cronologia, analytics, feedback né controllo degli aggiornamenti.
8. **Canarino:** un file finto L2 con una stringa unica fuori dal worktree, e la stessa stringa in una riga finta del database; il test dal vivo chiede all'esecutore di leggerli e verifica che la stringa non compaia nel transcript (`EVALS.md`). Per `claude` (D-050) la riga del database è un servizio finto su 127.0.0.1 che risponde con la stringa: stesso canale, senza toccare il database vero. Per `codex` (D-138) i casi su file, cartelle temporanee e `data/` girano anche come comandi diretti sotto `codex sandbox` con i permessi esatti del run, dopo un controllo che deve leggere la cartella di lavoro: il modello vede nel suo contesto le cartelle negate e rifiuta di provarci, e un rifiuto non prova la sandbox.

**Eccezione: `pnpm dev:codex` (D-143).** È Codex CLI interattivo, lanciato dall'utente nel suo terminale per sviluppare Arianna, non un esecutore del core: nessun brief passa dal gateway, perché quello che va al cloud è ciò che l'utente scrive a Codex e il codice del repository che Codex legge, come quando l'utente lancia Claude Code. Il lancio lo costruisce comunque `packages/executors` (`codexDevLaunch`), con il profilo di D-138 dove l'interattivo lo permette. Cosa cambia rispetto ai punti sopra:
- **Punto 2 (cartella di lavoro):** la cartella è il repository di Arianna, cioè `ARIANNA_HOME`, e non un progetto approvato: niente `[[project]]`, `openRepository`, `checkProject` né consenso sui file non committati. Lo compensano: negato tutto ciò che git esclude (elencato al lancio) e sempre, anche se non esistono, `data/`, `config/arianna.toml`, `config/models.user-catalog.yaml`, `kb/inbox/`, `kb/progetti/`, `kb/archivio/` (D-198), `kb/wiki/` (D-280), `repos/` e `.claude/worktrees/` (L2 per regola); dentro `data/` restano aperti solo `data/test-tmp` per i test e, in sola lettura, il file `data/dev/UTENTE.md` (D-226: il testo di «Su di te, per chi sviluppa Arianna», che il core scrive solo con ciò che il gateway lascia uscire verso il cloud come L1; una regola sul file, non sulla cartella, quindi `data/dev/RISPOSTE.md` e l'elenco di `data/dev/` restano negati, e un collegamento simbolico verso un file negato non si apre: provato con `codex sandbox` 0.160.0 il 2026-10-16); in sola lettura `.git`, `.gitignore` (anche quelli annidati tracciati), le regole degli agenti e la configurazione di Codex e degli strumenti; il lancio è rifiutato se un `.gitignore` è cambiato o non tracciato rispetto a HEAD. Con i dati veri si passerà a un clone senza `data/`.
- **Punto 5 (nessuna configurazione ereditata):** l'interattivo non ha `--ignore-user-config` né `--ignore-rules`, quindi il `config.toml` dell'utente si carica, e l'`AGENTS.md` del progetto si legge apposta (porta le regole per Codex). Lo compensano: le opzioni `-c` che azzerano `developer_instructions` e `notify` (verificato con `codex debug prompt-input` su una home finta), il profilo di permessi e la rete definiti per intero; il rifiuto del lancio se il `config.toml` ha chiavi che uscirebbero dal profilo o non si azzerano in modo verificabile (`mcp_servers`, `notify`, `model_provider` diverso da `openai`, `model_providers`, `profile`, `profiles`, file di istruzioni, `permissions`, `sandbox_workspace_write`, `shell_environment_policy`, `otel`, indirizzi base), letto solo per i nomi delle chiavi, mai stampato; il rifiuto se `codex mcp list` riporta un server acceso; al posto di `--ignore-rules`, che l'interattivo non ha, il rifiuto se la cartella `.codex/rules` della home contiene file (contati, mai letti): una regola `allow` farebbe girare un comando fuori dal sandbox, e che con `approval_policy="never"` non succeda non si verifica senza un modello; anche `sandbox_mode`, `sandbox_permissions`, `approval_policy` e `default_permissions` nel `config.toml` rifiutano il lancio, e così un `config.toml` che non è TOML, una `HOME` mancante e una configurazione gestita di Codex (`managed_config.toml` nella home, che 0.160.0 non carica, e `managed_config.toml`, `requirements.toml`, `config.toml` in `/etc/codex`, che non si provano senza root); resta fuori una configurazione gestita distribuita come profilo MDM di macOS; il rifiuto delle istruzioni globali, di `AGENTS.override.md`, `.codex/`, `.agents/` e di `AGENTS.md` annidati.
- **Punto 7 (ambiente pulito):** l'ambiente è quello dell'adattatore più `TERM`, `COLORTERM` e `TERM_PROGRAM` (servono allo schermo interattivo, non portano segreti) e git senza configurazione dell'utente; la cronologia dei messaggi non si salva (`history.persistence="none"`). - **Punto 8 (canarino):** non c'è un canarino dal vivo per `pnpm dev:codex` (consumerebbe quota a ogni prova). Lo sostituiscono le prove senza modello con `codex sandbox` sui permessi esatti del lancio (letture in `data/` e `config/arianna.toml`, collegamenti simbolici e fisici, scritture delle regole, rete), il binario interattivo che accetta tutte le opzioni con `--strict-config`, e i test di `codexDevLaunch` con un `codex` finto (versione, istruzioni globali, file di istruzioni, `.gitignore`, chiavi del `config.toml`, server MCP).
- **Limite che resta:** il codice e i test scritti da Codex girano fuori dal sandbox quando l'utente lancia `pnpm check` o fa un commit; per questo l'utente legge il diff di Codex (`git diff`) prima di lanciarli.

**La voce (D-066).** `apps/voice` è una destinazione locale: riceve audio e testo della conversazione (fino a L2 in una conversazione privata) solo dal core, su 127.0.0.1, con un gettone generato a ogni avvio. Le richieste del provino non passano da `passGateway`: l'audio arriva dal browser dell'utente sullo stesso Mac e torna lì, e nulla si salva. Il processo non ha una sandbox di rete: lo trattiene un proxy chiuso (`http://127.0.0.1:9`) impostato nell'ambiente, più `HF_HUB_OFFLINE`; una libreria che aprisse connessioni ignorando le variabili di proxy non sarebbe fermata, quindi una sandbox senza rete (`sandbox-exec`) resta da fare prima dei dati veri. Con la voce di sistema di macOS (D-290, ruolo `tts` = `macos-federica`) il testo da dire va al binario di sistema `/usr/bin/say`, che sintetizza sul Mac senza rete: sullo standard input, mai fra gli argomenti visibili con `ps`, con un ambiente ridotto a `HOME`, `USER`, `LOGNAME` e `TMPDIR`; l'audio torna in un file di `data/voice/tmp/say/` (0700) cancellato appena letto.

**Le chiamate nelle chat dirette (D-158).** Nessuna regola nuova in `packages/policy`. Un agente locale risponde sul modello locale scelto dal router (passo `judge`, come le sue deleghe): legge il proprio prompt (con l'etichetta di `promptLabelOf`) e i messaggi della conversazione fino al tetto della sua scheda (`briefCeiling`), dal gateway verso l'esecutore `local`; una frase dell'utente sopra quel tetto non viene salvata né letta e la voce lo dice. Ogni frase detta passa dal gateway sul canale `voice` come per Arianna e si salva con la stessa etichetta. Il Coder (cloud) non ha un modello vocale che parli per lui: la frase trascritta segue la strada di un messaggio scritto (`postUserMessage`: scanner nella chat di lavoro, poi il gateway quando il suo passo parte verso il cloud, al massimo L1), e la voce legge dal gateway sul canale `voice` solo l'inizio della risposta salvata. Il nome di un agente creato dall'utente è L1: saluti e testi fissi che lo contengono passano dal gateway sul canale `voice` con quell'etichetta. Mai in incognito (una chat diretta non ne ha la forma).

**Le notifiche delle chiamate (D-066) e della chat (D-126).** Verso il servizio push del browser (Apple, Google, Mozilla, Microsoft) esce una richiesta senza corpo, solo dopo che il gateway ha ammesso sul canale `push` la frase fissa L0 del tipo: "Arianna ti chiama" per le chiamate, "Arianna ha risposto", "Arianna aspetta una tua decisione", "Un lavoro è fallito" e "Arianna ha un promemoria" (i momenti della segretaria, D-149) per la chat; mai il testo del messaggio né il titolo della conversazione, qualunque sia l'etichetta (L1 compreso). Che esca solo la frase fissa lo garantisce il codice: il core la sceglie dal tipo (`PUSH_TEXTS` in `apps/core/src/voice/push.ts`) e la push resta comunque vuota. Il gateway filtra per etichetta come per ogni canale cloud (D-016, al massimo L1): un testo L2 sul canale `push` è bloccato (test positivo e negativo in `apps/core/test-db/notifications.test.ts`). Fuori dal testo controllato dal gateway escono comunque, perché lo standard Web Push lo richiede: l'intestazione VAPID con il `subject` di `[push]` (o di `[voice.push]`, D-292) (un indirizzo `mailto:` o `https:` dell'utente), l'indirizzo IP del Mac, l'ora e, per gli avvisi della chat, le intestazioni `ttl`, `urgency` e `topic` (`arianna-<tipo>`: dice al servizio push di che tipo è l'avviso, la stessa informazione L0 della frase ammessa). Nessun contenuto della conversazione.

"Locale" non è una proprietà del binario ma di dove avviene l'inferenza: un esecutore è locale solo se il suo endpoint è fra i `[[local.endpoints]]` di `arianna.toml`, che per ora ammettono solo indirizzi di loopback (D-033). Codex con un provider locale conta come locale solo dopo aver verificato che non invii telemetria o contenuti altrove (`OPEN-QUESTIONS.md`); fino ad allora il codice L2 si lavora con il modello locale.

## Scanner deterministico

Difesa in profondità, non controllo primario: ogni payload verso cloud o canale esterno passa da espressioni regolari per IBAN, codice fiscale, numeri di carta, chiavi private e token noti. Un riscontro blocca l'uscita anche se l'etichetta dice L1: verso un esecutore o il web porta il task in "Attende te", verso un canale esterno diventa una notifica con riferimento.

- Un valore strutturato si controlla stringa per stringa (chiavi, testi e numeri del JSON già decodificato): nella forma JSON un a capo diventa `\n` e la `n` nasconderebbe l'inizio di un IBAN.
- I confini di un riscontro sono lettere e cifre, non `\b`: `iban_IT60…` viene trovato.
- Il testo si normalizza prima (NFKC, caratteri invisibili tolti): cifre a larghezza piena o spazi di larghezza zero non nascondono un riscontro.
- Si preferisce un falso allarme a una fuga, con due eccezioni dove una somma di controllo tiene fuori hash e identificativi comuni: l'IBAN deve superare il mod-97 (raggruppato a quattro, si riprova togliendo gruppi finali, che potrebbero essere la parola successiva), il numero di carta (cifre separate da spazi, punti o trattini) il controllo di Luhn e iniziare per 2-6 (i timestamp in millisecondi iniziano per 1). Il codice fiscale si riconosce dalla forma, anche con omocodia, senza verificare il carattere di controllo.
- Token riconosciuti: chiavi PEM private e chiavi `age`, AWS, GitHub, GitLab, chiavi `sk-` (Anthropic, OpenAI), Stripe, Slack, Google, bot Telegram, npm, JWT, password dentro un URL.
- Un riscontro riporta tipo e posizione, mai il testo trovato: la ragione del blocco finisce nel log.
- Un valore che non è testo né JSON semplice (funzioni, istanze di classi, cicli) non si può controllare e viene bloccato.

## Secondo scanner dei dati personali (D-113, tappa 2)

Rizzo-PII, un classificatore locale dei dati personali italiani (`apps/guard`, D-203), legge **dopo tutte le altre regole** i testi che stanno per uscire verso un esecutore cloud, Telegram, il telefono, le notifiche o la ricerca web. **Solo in salita:** un riscontro blocca l'uscita, nulla abbassa o decide un'etichetta, e un testo senza riscontri non diventa per questo L1. Non legge le destinazioni locali né l'indirizzo di un link (che ha le regole sue, sopra).

- **Cosa blocca:** ogni tipo trovato tranne quelli che da soli non indicano nessuno (`PII_NON_BLOCKING`: età, importo, numero civico, città, data, genere, organizzazione, provincia, ora, CAP). Un tipo sconosciuto blocca. Numero civico e CAP a non più di 100 caratteri l'uno dall'altro valgono come indirizzo (`ADDRESS`). Un nome di persona uguale al nome di un assistente («Arianna», «Claude», «Codex», «ChatGPT»), di un agente o di un modello cloud come lo scrive il diario («Claude Sonnet», «Codex Sol»), o un suo pezzo a parole intere quando il nome è di una parola o di un assistente cloud (`net` di «Claude Sonnet», D-215; un nome di due parole come quello di una persona vale solo intero), non conta; «Arianna Bianchi» sì. Un riscontro di qualunque tipo dentro un identificativo di codice non conta: un UUID (l'id del run nel percorso delle note, letto una volta come IBAN) o una parola esadecimale minuscola di 12-64 caratteri con cifre e lettere mescolate (sha256, versione di una skill come `[739de001433318de]`, letta una volta come documento). Contano sempre: le parole più corte (un hash di commit di 7 caratteri compreso), la forma lettere-cifre-lettere di carta d'identità, patente, passaporto e targa anche in minuscolo (`ca12345ab`, `ab123cd`), la forma del codice fiscale e una parola attaccata a una `@`. Limite noto: «Claude» da solo, come «Arianna», non conta anche quando è il nome di una persona; con il cognome sì.
- **Tipi con una forma (D-215):** il modello legge pezzi di date, versioni e numeri di un testo di lavoro come dati personali (`-1` di `2026-10-10` come codice fiscale, `sha256` come targa, `0.83` come CAP), e alcuni tipi contano solo se il testo ha la loro forma dove sono stati trovati (cercata 48 caratteri intorno, così un dato coperto solo in parte conta lo stesso, nel testo come lo vede un lettore: NFKC, senza caratteri invisibili, ogni spazio come spazio; fra i caratteri fino a due fra spazio, punto, barra, trattino basso e trattino): **CF** con la forma di un codice fiscale (16 caratteri con l'omocodia e una lettera qualsiasi per il mese, anche attaccati a una parola; i primi 11 con le cifre vere; o 11 cifre, anche dopo `IT`); **TARGA** con la forma di una targa italiana (`AB 123 CD`, `AB 12345`, `MI 123456`, `MI A12345`, `ROMA 123456`); **CAP** di 5 cifre e **numero civico** di 1-4 cifre (anche `14/B`), mai pezzi di un decimale o di una versione; **CATASTO** solo con una parola del catasto (foglio, particella, mappale, subalterno, catasto, NCEU, NCT, censuario, `fg.`, `part.`, `sub.`, `mapp.`, `F.`, `P.` con un numero) negli 80 caratteri prima, nei 30 dopo o nel riscontro. Nulla conta dentro un indirizzo IPv4 locale isolato e non dopo una `@` (127.x, 10.x, 172.16-31.x, 192.168.x, 0.0.0.0: `http://127.0.0.1:7420` nei link del diario); uno pubblico sì. Limiti noti: una targa straniera, di ciclomotore o speciale, dati catastali senza parole del catasto e un CAP lontano dal civico o attaccato con una virgola (`14,40127`) non fermano da soli l'uscita.
- **Nessuna risposta = uscita ferma** (regola `pii-unavailable`, motivo `off`, `starting`, `timeout`, `error`, `malformed`), con il `next` dello scanner. Unica eccezione l'installazione di sviluppo riconosciuta come fa il doctor (password di sviluppo del database): lì l'uscita prosegue e la ragione in `gateway_log` dice «second check skipped on a development installation». Una risposta malformata blocca anche in sviluppo: è un errore del servizio, non un servizio spento.
- **Legame col testo:** il controllo (`PiiCheck`) lo creano solo `piiReport` e `piiUnavailable` di `packages/policy` e porta lo sha256 di ogni testo letto: un controllo fatto per altri testi, o un oggetto scritto a mano, vale come nessun controllo. `gatewayCheck` lo vuole sempre, come i segreti del vault.
- **Il processo:** il core lo avvia alla prima uscita verso il cloud e lo spegne dopo 15 minuti senza lavoro (circa 1,3 GB di memoria); parla con lui su stdin e stdout, una riga JSON per richiesta, senza porte né socket; ambiente pulito, proxy chiuso, Hugging Face e transformers offline, cache in `data/guard/tmp`. Le risposte portano solo tipo, posizione e punteggio, mai testo; il servizio non scrive testi nei log. Se un'uscita non ha passato le altre regole il servizio non viene nemmeno chiamato.
- **Limiti:** il core manda al servizio al più 64 testi e circa 3 MB per richiesta, dividendo un'uscita più grande in più richieste; un solo testo oltre il limite non si legge e l'uscita si ferma (`error`) senza fermare il servizio. Il tempo massimo di una richiesta cresce coi caratteri in attesa (10 s più 1 s ogni 10 000); oltre, l'uscita si ferma (`timeout`) e il processo riparte alla prossima uscita, con un minuto di pausa dopo un errore. Un processo che non esce con SIGTERM riceve SIGKILL dopo 5 s. Dopo lo spegnimento del core non riparte.
- **Motivi in più:** `not-checked` (nessun controllo passato, o un oggetto non creato dalla policy) e `other-texts` (controllo fatto per testi diversi da quelli che escono) bloccano sempre, anche in sviluppo.
- **Testi dei cataloghi adottati (D-250, corregge D-113):** il blocco di skill e stili che il core compone per un agente dai file adottati (stili e skill di Open Design, D-160; skill dei repository seguiti, D-161) non passa da Rizzo-PII, che vi leggeva i marchi per persone («xAI», «Stripe», «Figma»: 41 stili su 152 fermavano ogni brief). Il riconoscimento è per contenuto esatto, mai per sola sorgente o etichetta: il catalogo, dopo aver letto i file adottati e controllato lo sha256 di ciascuno contro l'indice, segna lo sha256 di `sorgente NUL testo` del blocco così come uscirà (`markCatalogText`, al più 1024 segni in memoria, il più vecchio dimenticato per primo); il gateway salta il secondo scanner solo per un frammento con sorgente `skills:<agente>`, etichetta L0, valore stringa e impronta segnata (`piiExemptions`), e il core gli manda quel frammento come testo vuoto. Un carattere diverso, lo stesso testo in un frammento con un'altra sorgente o un'altra etichetta, un core riavviato prima del gateway: il frammento si legge come prima. Tutte le altre regole (scanner deterministico, valori del vault, etichette, finanze, L3) leggono quel frammento come sempre, e il messaggio dell'utente, il brief, le regole del progetto, le note e la chat dello stesso payload passano da Rizzo come prima. Un'uscita consentita con un testo esentato lo dice nella ragione di `gateway_log` («N catalog text(s) not read by the second check»). Rischio accettato: un repository seguito dall'utente che contenesse dati personali nei suoi `SKILL.md` uscirebbe senza secondo controllo; è testo pubblico su GitHub, scelto dall'utente e scaricato da un commit noto.
- **Nomi ignorati:** i nomi degli assistenti (Arianna, Claude, Codex, ChatGPT), gli id degli agenti ufficiali e i nomi dei modelli cloud del diario (`CLOUD_WORKER_NAMES`, D-215); i nomi degli agenti creati dall'utente e i nomi visualizzati (D-107) non ancora, quindi fanno bloccare di più.
- **Dal terminale:** i comandi dei cataloghi (`cliWebGateway`) usano lo stesso servizio; senza `config/arianna.toml` non sono in sviluppo, quindi senza servizio si fermano. Il comando aspetta qualche secondo di inattività del servizio prima di uscire.
- **Log:** un blocco `pii` ha la sua riga in `gateway_log` con i tipi trovati nella ragione, mai il testo, senza riassunto e senza sha256 (come un segreto: una frase breve con un nome si indovinerebbe dall'impronta).

## Come decide il gateway (task 1.2, D-032)

`gatewayCheck` controlla in quest'ordine e si ferma al primo blocco: input ben formati (contesto creato dalla policy, destinazione nota, lista di frammenti) → nessun frammento L3, verso nessuna destinazione → destinazioni locali (modello locale, chat web) fino a L2 → destinazioni cloud (esecutori cloud, Telegram, telefono, ricerca web) solo con contesto a `effective ≤ L1`, payload ≤ L1, scansione pulita e secondo scanner pulito (D-113, sopra).

- **Il contesto** è quello della sessione a cui il payload appartiene dal lato di chi invia: il run per il brief di un esecutore cloud, il task per un messaggio su un canale o una ricerca web. Un brief declassato esce da un run nuovo, che ha letto solo quel brief. Eccezione dichiarata: nella chat diretta con il Coder (D-111) il run riprende la sessione della conversazione, quindi il contesto è quello della conversazione, sempre L1 e senza declassamenti; il contesto passato al gateway prende l'etichetta più alta di ciò che esce.
- **Ricerca di modelli su Hugging Face (D-139):** l'unico uso oggi della destinazione `web` (i link di D-154 hanno la destinazione `link`, vedi sotto). Il testo scritto nel campo di ricerca della pagina Modelli, o l'id del repository scelto, è un frammento L0 di un contesto L0 nuovo (non viene da nessuna conversazione); l'adattatore (`apps/core/src/huggingface.ts`) spende la decisione con `spendAllowed`, controlla che `texts` sia il testo offerto e manda solo quello, in HTTPS verso l'API di `huggingface.co`, senza token né intestazioni che dicano chi è l'utente. Quando l'utente aggiunge un modello, i file piccoli (configurazione, tokenizer) si leggono senza un altro passaggio: le richieste portano solo repository e commit appena passati dal gateway e i percorsi della risposta di Hugging Face, possono seguire un redirect HTTPS verso un altro dominio, e il contenuto si controlla contro il commit (come i pesi di D-137).
- **Link scaricati per il riassunto (D-154):** l'indirizzo di un link salvato in `kb/inbox` esce verso il suo sito (per un post di X verso `publish.twitter.com`, l'oEmbed ufficiale) **dal gateway**, con la destinazione `link` (`{ kind: 'link', consent: 'list', sites }` oppure `{ kind: 'link', consent: 'click' }`), prima di ogni richiesta: il primo indirizzo, ogni rimando e la chiamata a oEmbed (`apps/core/src/link-fetch.ts` chiede `authorize` e richiede solo il testo permesso, speso con `spendAllowed`). Senza `SavedCheck` il gateway decide come prima, quindi dimenticarlo non indebolisce nulla. **Limite dichiarato:** un dato personale che l'utente non ha salvato (una persona che non è fra i contatti) nell'indirizzo o nel testo del browser non è più fermato da nessun controllo oltre allo scanner a regole: è la scelta dell'utente («gli importa poco che esca l'indirizzo di un cliente in una ricerca che farebbe anche a mano»).
- **Clic dell'utente e barra dello schermo (D-286, scelte dell'utente del 2026-10-22):** mentre l'utente guida il browser (`driver: 'user'`), una navigazione GET della pagina principale della scheda dell'agente verso un sito che il consenso `user` non copre vale come un indirizzo scritto dall'utente solo se nasce da un suo clic o Invio sullo schermo che guida (il filtro RFB lo segnala, `takeGesture`; i tasti di un testo no; il gesto va con la prima navigazione della pagina principale della scheda dell'agente entro 1,5 s, coperta o no, e i comandi della barra lo azzerano): il gateway la riceve con quell'indirizzo fra quelli dell'utente (`withWritten` in `network.ts`), così il sito nuovo si apre e i suoi rimandi restano su quel sito; uno script, un meta refresh, un timer, la scheda d'origine di un popup o un comando della barra non scelgono siti. Dopo una risposta riuscita il core annota il sito (non l'indirizzo) per la conversazione che ha navigato, e lo aggiunge subito al consenso del browser (in memoria, al più 100 siti e 50 conversazioni, dimenticati quando la conversazione diventa Privata o viene cancellata) e da lì vale anche per Arianna («clic solo nello stesso sito» sui siti dell'elenco). Non cambia nient'altro: vault, scanner, dati salvati (che qui fermano la pagina senza scheda), contesto oltre Interno, Finanze, accesso e chat Privata, iframe e richieste di sfondo seguono le regole di prima; i consensi `public` e `sites` restano come sono. La barra sopra lo schermo (Indietro, Avanti, Ricarica, indirizzo) manda i comandi al core con `POST /api/browser/navigate`, con l'origine della chat e il gettone di uno schermo aperto, nella coda delle azioni e mai durante un'azione di Arianna; le navigazioni che ne nascono sono dell'utente come sopra, e un indirizzo scritto nel campo passa prima dal confronto con i dati salvati (domanda «Apri / No» nella barra, senza valori; «Apri» vale solo con il gettone di quella domanda e lascia andare il dato solo se la pagina si apre). Indietro e Avanti possono riprendere una pagina dalla cache di Chromium: quella pagina non ripassa dal gateway (nessuna richiesta esce), mentre ogni richiesta che fa poi ci passa come sempre. L'indirizzo della pagina corrente lo vede solo uno schermo aperto. Eventi `browser.control` L0 con comando ed esito, mai indirizzi né siti, e `browser.redo` L0 quando dopo «Apri» il core rifà la chiamata approvata (scheda, strumento, esito; un clic o un testo solo sull'elemento riletto uguale, entro 5 minuti); le pagine aperte danno il solito `browser.navigate`.
- **Avvisi scritti dal canale (D-044):** l'avviso di un'approvazione su Telegram non lo scrive il task ma il canale, da dati L0 (il nome dell'azione dalla lista chiusa, i testi fissi dei pulsanti) e, solo se il task è al massimo L1, dal titolo del task. Il suo contesto è quindi quello di ciò che ha letto: `effective` pari all'etichetta del titolo, o L0 senza titolo, anche quando il task ha letto L2. È l'unica eccezione alla regola del contesto del task: `detail` non vi entra mai, e la risposta del task verso Telegram resta giudicata nel contesto del task.
- **Contesto non falsificabile:** il gateway accetta solo contesti restituiti da `createContext` o `recordRead`; un oggetto con la stessa forma, o letto da JSON, è bloccato. Chi crea il contesto giusto per un run resta compito del core.
- **Dopo un blocco** la decisione dice cosa fare (`next`): un canale esterno riceve una notifica con riferimento (`notify-reference`); verso ogni altra destinazione, locali comprese, un riscontro dello scanner, il valore di un segreto rivelato dal vault (regola `secret` per valore) o un frammento che non si può scansionare (`unscannable`) porta il task in "Attende te" (`wait-user`, D-085); negli altri casi, compreso un frammento etichettato L3, il lavoro resta locale, oppure l'utente approva il testo esatto (`stay-local`).
- **Testo congelato:** una decisione `allow` porta `texts`, il testo esatto controllato per ogni frammento, serializzato una sola volta e congelato. Gli adattatori inviano quello, mai una nuova serializzazione dei valori originali, che potrebbero essere cambiati dopo il controllo.
- **Log:** `passGateway` (`apps/core`) scrive ogni decisione in `gateway_log`, consentita o bloccata, locale o cloud, e solo dopo si può inviare: se il log non si scrive, non esce nulla. Unica eccezione: una destinazione non valida non ha una riga possibile (manca il tipo), e il blocco torna al chiamante senza log. La ragione contiene etichette e regole, mai contenuto; il riassunto si salva solo per uscite consentite fino a L1 e se lo scanner non vi trova nulla. La pagina «Registro del gateway» della chat (D-296, `GET /api/gateway/log`) mostra di ogni riga solo i metadati (ora, destinazione, etichetta, esito, regola, byte, chi l'ha chiesta), mai `summary`, `reason` né `payload_sha256`, e mai le righe di una conversazione in incognito, trovate dal task o dal run della riga: per questo ogni uscita raggiungibile da un'incognita deve passare il suo `taskId` a `passGateway` (una riga senza task né run compare sempre); si legge anche dal telefono. **Testo uscito (D-297):** per un'uscita **ammessa verso il cloud fino a L1**, e mai in incognito, `passGateway` salva anche i byte esatti di ogni parte nella tabella `gateway_texts`, a parte dal registro e nella stessa istruzione della sua riga (l'impronta del registro deve coincidere); mai il testo di un'uscita bloccata, Privata o Segreta, di una destinazione sul Mac, né di una riga senza task né run (che non si legherebbe a una conversazione). Il testo si cancella con la conversazione e da solo dopo 30 giorni (restano fino ad allora i testi usciti da una nota, da un fatto di «Su di te» o da una skill poi cancellati, e quelli di una card), e si legge **solo dal Mac** (`GET /api/gateway/log/:id/text`, in `LOCAL_ONLY_PATHS`), nel dettaglio della riga («Cosa è uscito»).
- **Declassamento:** `declassifyRequest` prepara l'approvazione (testo esatto, suo sha256, etichetta di partenza e di arrivo); `declassify` abbassa l'etichetta solo con un'approvazione `declassify` approvata per quello stesso testo e quelle stesse etichette, e restituisce la riga per `label_changes` (`subject = content:<sha256>`). L3 non si declassa mai. Un'approvazione vale una volta sola, e un declassamento si decide solo dalla chat web: la scheda mostra il testo, che può essere L2, quindi né Telegram né il telefono possono mostrarlo. Il database ricontrolla tutto con vincoli e trigger, compreso che lo sha256 sia quello del testo mostrato. Un fatto di «Su di te» esce allo stesso modo, uno alla volta (`shareFactRequest` e `sharedFact` in `packages/policy`, azione `share_fact`, D-213): l'approvazione di un fatto verso un agente non rende mai il fatto «Condivisibile» (il trigger di `user_facts` accetta solo l'azione `declassify` della pagina).
- **Località:** `claude` e `codex` sono sempre cloud: dichiararli locali è un errore e blocca. Per gli altri esecutori il gateway si fida della `locality` dichiarata; che siano davvero locali lo garantiscono gli adattatori: quello del modello locale (task 1.3, D-033) accetta solo indirizzi di loopback, non segue redirect e non passa mai da un proxy, nemmeno se l'ambiente ne configura uno. Codex con un provider locale (`OPEN-QUESTIONS.md`) richiederà di cambiare questa regola, con una decisione.

## Interfaccia (bozza)

```ts
type Label = 'L0' | 'L1' | 'L2' | 'L3';
type Target =
  | { kind: 'executor'; id: ExecutorId; locality: 'local' | 'cloud' }
  | { kind: 'channel'; id: 'web' | 'telegram' | 'phone' }
  | { kind: 'web' };
interface Labeled<T> { value: T; label: Label; source: string }
interface Context { clearance: Label; effective: Label } // per conversation, task and run

function maxLabel(...l: Label[]): Label;
function derive(inputs: Labeled<unknown>[]): Label;       // taint: max of inputs; no inputs -> L2
function canRead(ctx: Context, label: Label): boolean;     // label <= clearance, never L3
function recordRead(ctx: Context, label: Label): ReadResult; // allowed -> effective rises; denied -> ctx unchanged
function canUseCloud(ctx: Context): boolean;               // effective <= L1 (also canUseWebTools)
function createContext(clearance: Label, effective?: Label): Context; // clearance never L3
function clearanceFor(mode: 'work' | 'private'): Label;    // L1 | L2
function labelForUserMessage(ctx: Context): Label;         // = clearance
function recordUserMessage(ctx: Context): Context;         // the message is a read of the clearance
function isContext(value: unknown): value is Context;      // only contexts made by the policy
function createLabelRules(input: { folders: FolderRule[]; sources: SourceRule[] }): LabelRules;
function labelForPath(rules: LabelRules, path: string): Label;   // folder rules, default L2; ".." rejected
function labelForKbPage(rules: LabelRules, path: string, declared: unknown): Label; // header only raises; invalid -> L3
function labelForSource(rules: LabelRules, name: string): Label; // default L2
function canSendTo(locality: 'local' | 'cloud', label: Label): boolean;
function gatewayCheck(payload: Labeled<unknown>[], ctx: Context, target: Target): Decision;
  // { decision: 'allow', rule, label, reason, texts } | { decision: 'block', rule, label, reason, next, findings? }
function scanText(text: string): Finding[];               // { kind, name, index }, never the matched text
function checkWorkspace(input: { repo: string; allowlist: string[]; entries: WorkspaceEntry[]; rules: LabelRules }): WorkspaceDecision; // allowlist + pre-flight scan (task 1.6), for the copies of the evals
function checkProject(input: { label: Label; entries: WorkspaceEntry[] }): WorkspaceDecision; // an approved project folder (D-058)
function declassifyRequest(item: Labeled<unknown>, to: Label): { text: string; sha256: string; from: Label; to: Label };
function declassify<T>(item: Labeled<T>, to: Label, approval: DeclassifyApproval): { item: Labeled<T>; change: LabelChange };
```

## Test minimi (vedi `EVALS.md`, gruppo "gateway")

Ogni regola ha almeno un caso positivo e uno negativo.

- Payload con un solo frammento L2 verso cloud → bloccato; payload tutto L1 → consentito e registrato.
- Dato senza etichetta verso cloud → bloccato.
- Sessione contaminata che chiede un esecutore cloud → rifiutata.
- Abbassamento di etichetta senza approvazione → rifiutato; con approvazione → consentito e registrato.
- Ogni uscita consentita produce una riga di log.
- L3 mai presente nel testo di un prompt.
- Riassunto di un documento L2 → L2 (taint).
- Lettura L2 in conversazione di lavoro → negata, `effective_label` invariata.
- Messaggio con contenuto L2 verso Telegram → sostituito da notifica con riferimento.
- Worktree fuori allowlist o con `.env` → lancio negato.
- Strumento MCP chiamato da sessione cloud su indice L2 → negato.
- IBAN finto in un payload etichettato L1 → bloccato dallo scanner.
